# 积分权益运营系统 · 后端整体架构设计

> 技术栈：**SpringBoot 3.2 + MySQL 8 + Redis + Redisson + RocketMQ 5.x**
> 包结构基准：`com.heima.jifenquanyi`
> 部署形态：模块化单体（Monolith-First，单应用多 Module 分包），可平滑拆分微服务

│ 从库(读) │  │ ②分布式Session   │   │ ②异步消息：积分流水/通知/日志    │
│          │  │ ③Lua原子扣库存   │   │ ③削峰：秒杀异步创建订单         │
│ 5大表+   │  │ ④幂等Key/SETNX  │   │ ④事务消息：积分增减一致性        │

└──────────┘        ▲Redisson(RLock)

数据流向要点：
- **读多写少**（商品详情、积分余额）：Cache Aside，先查 Redis，miss 回源 DB 并回填。
- **写密集**（积分流水、秒杀订单）：DB 承担最终落库，Redis/RocketMQ 前置缓冲。
- **跨服务一致性**：RocketMQ 事务消息 + 幂等消费，保证"账户增减 + 流水"最终一致。

## 三、每个中间件详细作用与解决的线上 Bug

### 3.1 Redis（缓存 + 分布式 Session + 原子操作）

**缓存策略：Cache Aside + 逻辑过期**

读：`Redis GET → 命中返回 → 未命中查 DB → 回填 Redis`。
写：`先更新 DB → 删除 Redis 缓存（或延迟双删）`。

| 线上痛点 / Bug | 根因 | Redis 落地方案 |
|---|---|---|
| **缓存穿透**：恶意大量查询不存在 key（如乱序 user_id） | 缓存 miss 后全部打到 DB | ① 布隆过滤器预热合法 id，过滤非法 key；② 对不存在的 key 缓存空值（TTL 60s），拦截后续请求 |
| **缓存击穿**：秒杀商品/热点活动 key 在过期瞬间被高并发命中 | 单热点 key 过期重建，DB 被打满 | **逻辑过期**：key 永不过期，value 内带 expire 字段；重建时加 **Redisson 互斥锁**，只允许一个线程回源重建，其余短暂等待读旧值 |
| **缓存雪崩**：大量 key 同一时间集体过期 | 缓存全部失效打垮 DB | ① TTL 加随机因子（基础 TTL ± 300s 抖动）；② 热点 key 用逻辑过期+后台异步刷新；③ 多级缓存（本地 Caffeine + Redis） |
| **重复领取/超领** | 多实例并发写无原子性 | Redis **Lua 脚本原子扣减**、`SETNX` 幂等键（详见第五章） |

**Redis 分布式 Session（解决多服务器集群登录不同步）**
- 痛点：多实例部署时，Session 存在各自 JVM 内存，用户在一台机器登录后请求被转发到另一台机器即"掉线"；传统 Tomcat Session 复制方案广播成本高、数据不一致。
- 落地：登录成功后把 `sessionId → {userId, 昵称, 头像, 有效期}` 写入 Redis（`SET session:{token}  json  EX 7d`，每次请求续期）；`LoginInterceptor` 从 Redis 取 Session，命中即放行并刷新 ThreadLocal。
- 扩展：可替换为 Spring Session Data Redis + Redisson，天然支持集群一致性、会话失效监听。

### 3.2 Redisson（分布式锁）

| 场景 | 使用的锁 | 解决 Bug |
|---|---|---|
| 秒杀 **一人一单** | `RLock lock = redisson.getLock("seckill:user:" + userId + ":" + activityId)` | 同一用户并发多次点击，锁保证只放行一次下单 |
| 防重复领任务积分 | `RLock("task:user:" + userId + ":" + taskId + ":" + date)` | 集群多实例并发领取，锁 + 幂等键双保险 |
| 过期积分回收任务 | `RLock("point:expire:run")` + `tryLock(0, 30s)` | 多节点定时任务同时触发，只允许一个节点执行 |
| 热点 key 缓存重建 | `RLock("cache:rebuild:" + key)` | 只让一个线程回源 DB，防击穿 |

Redisson 优势（相对原生 `SETNX`）：
- **可重入**：同一线程可重复加锁（服务内嵌套调用不互卡）。
- **WatchDog 自动续期**：业务执行超过默认 30s 锁时，自动续期，防止长任务期间锁提前释放导致并发问题。
- **可等待 + 公平锁**：秒杀场景可设置 `tryLock` 等待时间，失败立即返回"手慢了"。
- 底层加锁/释放锁均为 **Lua 脚本原子执行**，杜绝"加锁成功但过期被误删他人锁"的问题。

### 3.3 RocketMQ（异步解耦 + 延时 + 削峰 + 事务）

| 用途 | 场景 | 解决 Bug |
|---|---|---|
| **延时队列** | 积分发放时按 `expireTime` 投递**延时消息**，到点触发**积分过期回收** | 避免高频定时扫表耗 DB；精确到每条积分流水独立过期 |
| **延时队列** | 秒杀订单超时未支付自动取消（30 分钟）并回滚库存 | 释放无效占用的库存 |
| **异步解耦** | 签到/任务发积分后，异步写流水 + 发短信/站内信 | 主链路不等通知，吞吐提升，DB 削峰 |
| **削峰填谷** | 秒杀请求只做"Lua 扣库存"成功后，**发送消息异步创建订单** | 秒杀瞬时 10w QPS 打不垮 MySQL，订单创建平摊到消费端 |
| **事务消息** | 扣减积分 ↔ 生成兑换/秒杀订单必须同生共死 | 半消息机制保证本地事务与 MQ 投递最终一致，防止"钱扣了订单没建" |

消费端配套：**消费幂等**（按 `msgId`/业务号去重）+ **重试机制** + **死信队列**（对账失败告警人工介入）。

## 四、数据库设计思路

### 4.1 表清单与索引设计

| 表 | 用途 | 必建索引 | 为什么建 |
|---|---|---|---|
| `t_user` | 用户 | `uk_phone`（唯一） | 登录/注册按手机号精准查询；唯一约束防重复注册 |
| `t_user_session` | 登录会话 | `idx_token`（唯一） | 按 token 高频反查用户，O(log n) 定位会话 |
| `t_point_account` | 积分账户 | `uk_user_id`（唯一）+ `version`（乐观锁字段） | 一用户一账户；更新用乐观锁防并发扣减超扣 |
| `t_point_flow`（**大表**） | 积分流水 | `idx_user_time (user_id, create_time DESC)`；`uk_flow_no`；`idx_expire (expire_time, status)` | 明细查询永远带 user_id + 时间排序，避免全表扫描；flow_no 幂等；过期回收按 expire_time 扫描 |
| `t_sign_in_record` | 签到记录 | `uk_user_date (user_id, sign_date)` | 唯一索引天然实现"一天只能签到一次"，防重复发积分 |
| `t_task` | 任务配置 | `uk_task_code` | 任务码唯一 |
| `t_task_record` | 任务领取记录 | `uk_user_task_date (user_id, task_id, task_date)` | 幂等兜底：同人同任务当天只能领一次 |
| `t_product` | 商品 | `idx_status (status, point_price)` | 上架商品列表按状态过滤分页 |
| `t_exchange_record` | 兑换记录 | `idx_user_time (user_id, create_time)`；`uk_exchange_no` | 我的兑换列表高频查询；订单号幂等去重 |
| `t_seckill_activity` | 秒杀活动 | `idx_start_end (start_time, end_time)` | 查询"进行中的活动"，避免对全表扫日期 |
| `t_seckill_order` | 秒杀订单 | `uk_user_activity (user_id, activity_id)`；`uk_order_no` | **一人一单的最后防线**，数据库唯一约束兜住 Redis 锁的全部漏网之鱼 |
| `t_stock` | 库存 | `uk_biz (biz_type, biz_id)`；`version` | 唯一库存记录；乐观锁扣减（`WHERE stock > 0`） |
| `t_point_expire_record` | 过期回收记录 | `idx_expire_status (expire_time, status)` | 回收任务按到期时间 + 未处理状态扫描，避免全表 |
| `t_reconcile_record` | 对账结果 | `idx_batch (batch_no)` | 按批次对账结果查询 |

### 4.2 核心表结构要点（以积分流水为例）

```sql
CREATE TABLE `t_point_flow` (
  `id`            BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `flow_no`       VARCHAR(64)  NOT NULL COMMENT '流水号(全局唯一,幂等键)',
  `user_id`       BIGINT       NOT NULL COMMENT '用户id',
  `biz_type`      TINYINT      NOT NULL COMMENT '业务类型:1签到 2任务 3兑换 4过期回收',
  `change_point`  INT          NOT NULL COMMENT '变动积分(+增加/-减少)',
  `balance_after` INT          NOT NULL COMMENT '变动后余额(对账用)',
  `source_type`   TINYINT      NOT NULL COMMENT '来源:1普通 2秒杀',
  `source_id`     BIGINT       NOT NULL COMMENT '业务来源id(订单号/任务id)',
  `expire_time`   DATETIME     DEFAULT NULL COMMENT '本笔积分过期时间(NULL=永不过期)',
  `status`        TINYINT      NOT NULL DEFAULT '1' COMMENT '1有效 2已回收',
  `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_flow_no` (`flow_no`),
  KEY `idx_user_time` (`user_id`, `create_time` DESC),
  KEY `idx_expire` (`expire_time`, `status`)
) ENGINE=InnoDB COMMENT='积分流水表';
```

**大表治理**：`t_point_flow` 按 `user_id % 64` 分表或按季度归档冷数据；明细查询强制带 `user_id` 走索引；列表接口只查索引覆盖列，详情再回表。

### 4.3 索引设计三原则
1. **查询条件**用到的列建索引（`WHERE user_id=? AND sign_date=?` → 联合索引）。
2. **排序/分页**列进索引（`ORDER BY create_time DESC` → 避免 filesort）。
3. **幂等去重**用唯一索引，而不是靠应用层判断（唯一索引是并发兜底）。

## 五、高并发方案汇总

### 5.1 抢购防超卖（秒杀）

```
请求进入
  │
  ▼
① 网关限流(按用户/IP 令牌桶) + 布隆过滤器挡无效商品id
  │
  ▼
② 活动校验：Redis 读活动状态(start<=now<=end) + 已售罄标记  → 未开始/结束直接拒绝
  │
  ▼
③ Redisson 分布式锁：lock("seckill:user:{userId}:{activityId}")  → 实现一人一单
  │
  ▼
④ Lua 脚本原子预扣库存：DECR key("stock:{activityId}") 并校验 >=0
  │         └─ 小于0 → 标记售罄(SET 售罄key)，返回"已抢光"
  │
  ▼
⑤ 发送 RocketMQ 消息(削峰)：OrderCreateMsg{userId, activityId, orderNo}
  │         └─ 主链路立即返回"抢购成功，等待出单"
  ▼
⑥ 消费者异步：幂等查重(uk_user_activity) → 创建 t_seckill_order → 
    DB 库存乐观锁兜底 UPDATE t_stock SET version=version+1,
    available=available-1 WHERE biz_id=? AND available>0
    → 写积分流水 → 发通知
```

**四层防线**：Redis Lua 预扣 → MQ 削峰 → DB 乐观锁兜底 → 唯一索引一人一单。
**回滚**：超时未支付 → 延时消息取消订单 → 库存 `INCR` 回补；Redis 售罄标记在活动结束后删除。

### 5.2 防重复领积分（签到/任务）

```
用户点击"签到 / 领取任务"
  │
  ▼
① Redis 幂等键：SETNX sign:{userId}:{date}=1  EX 2d（Lua 保证原子）
  │        └─ 返回0 → 已签到/已领取，直接拒绝
  ▼
② Redisson 分布式锁：lock("task:user:{userId}:{taskId}:{date}")（双保险）
  │
  ▼
③ 本地事务：插入 t_sign_in_record / t_task_record（撞唯一索引抛 DuplicateKeyException → 回滚提示重复）
  │
  ▼
④ 更新 t_point_account（乐观锁 version）+ 写 t_point_flow（balance_after）
  │
  ▼
⑤ 发送 RocketMQ：延时消息(按积分 expireTime)触发过期回收 + 异步通知
```

**三层防线**：Redis 幂等键（快速拦截）→ 分布式锁（串行化）→ 数据库唯一索引（最终兜底）。

### 5.3 过期积分回收完整执行流程

```
方案A（推荐）：RocketMQ 延时消息驱动
────────────────────────────────────
发放积分写流水时，按 expire_time 计算延迟投递延时消息 ExpireMsg{flowNo, userId, point}
  → 到点消费：①分布式锁 lock("point:expire:run:{flowNo}")
            ②查 t_point_flow 状态，status=已回收 → 跳过(幂等)
            ③Redisson 锁住用户账户 → 更新 t_point_account(总积分减、过期积分增)
            ④写负向流水 balance_after + 写 t_point_expire_record(已回收)
            ⑤发通知(站内信/短信)

方案B：定时任务驱动（兜底，防延时消息丢失）
────────────────────────────────────
XXL-Job 每 5 分钟扫描 t_point_flow WHERE expire_time<=NOW() AND status=1 LIMIT 500
  → 获取全局分布式锁 lock("point:expire:run")，防多节点重复执行
  → 按上述 ③④⑤ 批量回收 → 更新 scan cursor，避免重复扫描
```

**一致性保障**：回收记录唯一（flowNo）+ 状态机（1有效→2已回收）幂等；账户扣减与负向流水同事务。
**对账闭环**：日终 `ReconcileService` 校验 账户余额 == 累计流入 − 累计流出 − 累计过期回收，差异进 `t_reconcile_record` 并告警。
